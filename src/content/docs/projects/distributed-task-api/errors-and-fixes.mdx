## Incident 1: Database Connection Pool Exhaustion Under Concurrent Load

  <div class="rca-header">
    <svg xmlns="http://www.w3.org/2000/svg" width="18" height="18" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><circle cx="12" cy="12" r="10"></circle><line x1="12" y1="8" x2="12" y2="12"></line><line x1="12" y1="16" x2="12.01" y2="16"></line></svg>
    <span>1. Symptom & Exact Error</span>
  </div>
  <p>Under simulated load testing (500 concurrent users), the service stopped responding and application logs filled with:</p>
  <pre><code>ERROR [db_pool] pool timeout: connection pool exhausted (max_size=10)
  at Pool.acquire (/app/node_modules/pg-pool/index.js:142:19)
  at async UserService.getUserProfile (/app/src/services/user.service.js:45:18)
HTTP/1.1 504 Gateway Timeout (TTFB: 30,002ms)</code></pre>
</div>

<div class="rca-box rca-misleading">
  <div class="rca-header">
    <svg xmlns="http://www.w3.org/2000/svg" width="18" height="18" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><path d="m21.73 18-8-14a2 2 0 0 0-3.48 0l-8 14A2 2 0 0 0 4 21h16a2 2 0 0 0 1.73-3Z"></path><line x1="12" y1="9" x2="12" y2="13"></line><line x1="12" y1="17" x2="12.01" y2="17"></line></svg>
    <span>2. Misleading Clues</span>
  </div>
  <p>CPU and memory usage on both the API pods and the PostgreSQL server were below 15%. The team initially suspected network firewall packet drops between Kubernetes worker nodes.</p>
</div>

### 3. Investigation & Diagnostic Commands

```bash
# 1. Inspect live PostgreSQL connection states
psql $DATABASE_URL -c "SELECT state, count(*) FROM pg_stat_activity GROUP BY state;"

# 2. Check connections in 'idle in transaction' state
psql $DATABASE_URL -c "SELECT pid, state, age(clock_timestamp(), state_change), query FROM pg_stat_activity WHERE state = 'idle in transaction';"
```

**Observation:** 10 connections were stuck in `idle in transaction` for over 15 minutes each.

### 4. Root Cause Analysis (RCA)

An async error inside an unhandled promise rejection in `UserService.getUserProfile` threw an error *after* `pool.connect()` was called but *before* the transaction commit/rollback could execute. Because the `finally` block did not call `client.release()`, the connection was leaked forever until process termination.

<div class="rca-box rca-fix">
  <div class="rca-header">
    <svg xmlns="http://www.w3.org/2000/svg" width="18" height="18" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><path d="M22 11.08V12a10 10 0 1 1-5.93-9.14"></path><polyline points="22 4 12 14.01 9 11.01"></polyline></svg>
    <span>5. The Verified Fix</span>
  </div>
  <p>Implemented the RAII / scope-guard pattern ensuring client release in <code>finally</code> and introduced automatic transaction wrappers:</p>
</div>

```javascript
// BEFORE (Vulnerable to connection leaks)
const client = await pool.connect();
await client.query('BEGIN');
const user = await findUser(client, id);
await client.query('COMMIT');
client.release(); // Skipped if findUser throws!

// AFTER (Guaranteed cleanup)
const client = await pool.connect();
try {
  await client.query('BEGIN');
  const user = await findUser(client, id);
  await client.query('COMMIT');
} catch (err) {
  await client.query('ROLLBACK');
  throw err;
} finally {
  client.release(); // Always executed
}
```

### 6. Prevention Guardrail

- Added ESLint rule `no-floating-promises` and a unit test harness asserting connection pool returns to 0 active checkouts after simulated service failures.
- Configured PostgreSQL server-side: `idle_in_transaction_session_timeout = '15s'`.

## Incident 2: JWT Refresh Token Expiration Miscalculation

<div class="rca-box rca-error">
  <div class="rca-header">
    <svg xmlns="http://www.w3.org/2000/svg" width="18" height="18" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><circle cx="12" cy="12" r="10"></circle><line x1="12" y1="8" x2="12" y2="12"></line><line x1="12" y1="16" x2="12.01" y2="16"></line></svg>
    <span>1. Symptom & Exact Error</span>
  </div>
  <p>Users reported frequent unexpected logouts even while actively using the application:</p>
```json
{
  "status": 401,
  "code": "TOKEN_EXPIRED",
  "message": "jwt expired: current timestamp 1731500000 > exp 1731471200"
}
```
</div>

<div class="rca-box rca-misleading">
  <div class="rca-header">
    <svg xmlns="http://www.w3.org/2000/svg" width="18" height="18" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><path d="m21.73 18-8-14a2 2 0 0 0-3.48 0l-8 14A2 2 0 0 0 4 21h16a2 2 0 0 0 1.73-3Z"></path><line x1="12" y1="9" x2="12" y2="13"></line><line x1="12" y1="17" x2="12.01" y2="17"></line></svg>
    <span>2. Misleading Clues</span>
  </div>
  <p>The token configuration had set <code>REFRESH_TOKEN_TTL=7d</code>. The team assumed client device clock drift.</p>
</div>

### 3. Investigation

```bash
echo "eyJhbGciOi..." | jwt decode -
# Output:
# "iat": 1731471200,
# "exp": 1731471207  <--- Only 7 SECONDS later!
```

### 4. Root Cause Analysis

The JWT helper received `REFRESH_TOKEN_TTL_MS = 7 * 24 * 60 * 60 * 1000`. However, the signing library expected duration in **seconds**, not milliseconds. Passing raw millisecond integers caused a timestamp overflow wrapping issue.

<div class="rca-box rca-fix">
  <div class="rca-header">
    <svg xmlns="http://www.w3.org/2000/svg" width="18" height="18" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><path d="M22 11.08V12a10 10 0 1 1-5.93-9.14"></path><polyline points="22 4 12 14.01 9 11.01"></polyline></svg>
    <span>5. The Verified Fix</span>
  </div>
  <p>Fixed token issuance with explicit unit string: <code>jwt.sign(payload, secret, &#123; expiresIn: '7d' &#125;)</code></p>
</div>

### 6. Prevention Guardrail

Added CI tests asserting token duration bounds:
```typescript
test('refresh token exp must be at least 6 days in future', () => {
  const token = generateRefreshToken(mockUser);
  const decoded = jwt.decode(token);
  expect(decoded.exp - decoded.iat).toBe(7 * 24 * 3600);
});
```
